# Milvus 대신 Qdrant를 사용하는 이유

**Milvus 대신 Qdrant를 선택하는 가장 큰 이유는 '압도적인 가벼움(운영 편의성)'과 '강력한 메타데이터 필터링 성능' 때문입니다.**

특히 **보험 약관 RAG 시스템**처럼 수만~수백만 건 규모의 문서에서 특정 조건(`strict_filter`: 보험사명, 상품명, 가입 연도 등)을 걸어 빠르게 검색해야 하는 환경에서는 Qdrant가 훨씬 유리한 경우가 많습니다.

---

## 1. Milvus vs Qdrant 핵심 비교

| 비교 항목 | Qdrant | Milvus |
| :--- | :--- | :--- |
| **개발 언어** | **Rust** (가볍고 빠르며 메모리 효율이 뛰어남) | Go / C++ (대규모 분산 처리에 초점) |
| **인프라 및 배포** | **단일 바이너리 / 도커 컨테이너 1개**로 즉시 실행 | etcd, MinIO, Pulsar/Kafka 등 **의존성 컴포넌트가 많음** |
| **운영 난이도** | 매우 쉬움 (중소규모~수천만 건 규모에 최적) | 높음 (쿠버네티스 환경 및 전담 인프라 인력 권장) |
| **필터링 성능** | **매우 뛰어남** (HNSW 그래프 탐색 중 필터를 동시에 적용) | 대규모 분산 환경에서는 강하나 소규모에선 오버헤드 존재 |
| **데이터 규모** | 수만 ~ 수억 건 수준에 적합 | 수억 ~ 수십억 건 이상의 초대규모 엔터프라이즈에 적합 |

---

## 2. 보험 약관 프로젝트에서 Qdrant가 유리한 3가지 이유

1. **가볍고 빠른 구축 및 유지보수**
   * Milvus는 분산 아키텍처로 설계되어 기본적으로 띄워야 하는 부속 서비스(메타데이터 저장소, 오브젝트 스토리지, 메시지 큐 등)가 많아 무겁습니다.
   * 반면 Qdrant는 Rust로 작성되어 가볍고, Docker 컨테이너 하나만 띄우면 바로 운영 수준으로 쓸 수 있어 개발 속도와 유지보수 비용을 크게 줄여줍니다.

2. **`strict_filter` (메타데이터 필터링) 최적화**
   * 보험 약관 검색은 *"2024년 삼성화재 실손보험"*처럼 메타데이터 조건(`query_filter=strict_filter`)을 먼저 거른 뒤 유사도를 찾는 작업이 필수적입니다.
   * Qdrant는 벡터 인덱스와 페이로드(메타데이터) 인덱스를 긴밀하게 통합하여, 복잡한 필터 조건을 걸어도 검색 속도와 정확도가 떨어지지 않도록 설계되어 있습니다.

3. **직관적인 JSON 기반 Payload 구조**
   * Milvus는 일반 RDBMS처럼 엄격한 스키마(Schema)를 미리 정의해야 해서 컬럼 추가나 수정이 번거롭습니다.
   * Qdrant는 문서의 부가 정보(조항 번호, 페이지, 상품 코드 등)를 자유로운 JSON 형태(`Payload`)로 저장할 수 있어 데이터 파이프라인을 유연하게 구성하기 좋습니다.

---

## 💡 요약: 언제 무엇을 쓰나요?

* **Qdrant 추천:** 수천만 건 이하의 데이터, 빠르고 가벼운 인프라 구축, 복잡한 메타데이터 필터링(`query_filter`)이 중요한 서비스 (대부분의 기업용 RAG 프로젝트)
* **Milvus 추천:** 수억~수십억 건 이상의 초대용량 벡터 데이터를 여러 서버에 분산해서 처리해야 하고, 이를 관리할 인프라/DevOps 팀이 있는 경우
