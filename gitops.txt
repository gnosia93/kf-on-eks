GitOps 도구를 쓴다는 것은 Git 저장소를 유일한 기준(Single Source of Truth)으로 삼아, Git에 코드를 올리면 전용 도구가 이를 감지해 쿠버네티스 환경에 자동으로 배포하고 상태를 일치시키는 방식을 말합니다.
개발자가 터미널에서 kubectl apply 같은 명령어를 직접 치는 대신, Git의 변경 사항을 자동화 도구가 대신 클러스터에 반영해 주는 구조입니다.

1. GitOps의 핵심 동작 원리

• Git이 곧 실제 환경: 쿠버네티스 클러스터에 어떤 앱이 떠 있어야 하는지, 설정값(ConfigMap 등)이 무엇인지를 모두 Git 저장소의 YAML 파일이나 코드로 정의해 둡니다.
• 자동 동기화(Sync): 클러스터 내부에 설치된 GitOps 전용 에이전트가 Git 저장소를 24시간 감시합니다.
• 변경 감지 및 배포: 개발자가 Git에 수정된 내용을 push하면, 도구가 이를 즉시 알아채고 클러스터의 상태를 Git의 최신 내용과 똑같이 자동으로 업데이트합니다.

2. 대표적인 GitOps 도구

실무에서 쿠버네티스와 함께 가장 많이 쓰이는 두 가지 도구가 있습니다.
• Argo CD: 현재 가장 대중적인 도구로, 웹 화면(UI)을 통해 Git의 코드와 실제 쿠버네티스 클러스터의 상태가 일치하는지 시각적으로 한눈에 보여줍니다.
• Flux: UI 없이 가볍게 백그라운드에서 동작하며 Git 저장소와 클러스터를 자동으로 동기화해 주는 도구입니다.

3. 앞서 질문하신 방식과의 차이점

• 직접 git clone (컨테이너 내부): 파드(컨테이너)가 실행될 때마다 각 파드가 직접 Git에 접속해서 코드를 긁어오는 방식입니다. 파드가 100개 뜨면 Git에도 100번 접속해야 해서 비효율적이고 네트워크 문제에 취약합니다.
• GitOps 도구 사용 (Argo CD 등): 클러스터의 관리자 역할을 하는 GitOps 도구만 Git을 바라봅니다. Git에 코드가 올라오면 도구가 먼저 새 도커 이미지를 만들거나 ConfigMap을 업데이트한 뒤, 쿠버네티스에 "이제 이 새 버전으로 파드들을 교체해!"라고 명령을 내립니다.

4. 실무에서 GitOps를 쓰는 이유

• 명령어 실수 방지: 사람이 직접 터미널에 kubectl 명령어를 입력하다가 운영 서버를 잘못 건드리는 사고를 원천 차단합니다.
• 완벽한 이력 관리와 롤백: 모든 배포 기록이 git commit 기록으로 남습니다. 배포 후 문제가 생기면 git revert 명령어로 Git 코드만 이전으로 되돌리면 클러스터도 수 초 만에 과거 버전으로 안전하게 복구됩니다.
